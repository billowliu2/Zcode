# 需求梳理与设计对话（Brainstorming）

把想法变成设计。核心是**协作对话**：你（主代理）负责提问、给方案、呈现设计；用户负责回答与确认；researcher 负责把事实性问题查实。**在对话产出明确设计之前，不写任何实现代码。**

## 与相邻机制的边界

| 机制 | 定位 | 何时用 |
|---|---|---|
| **brainstorming（本技能）** | 模糊想法 → 明确设计 | "我想做个 X"（需求不完整） |
| ZCode 计划模式（EnterPlanMode） | 明确需求 → 实施计划 | 需求清楚、要做技术方案 |
| `task-execute` | 执行计划 | "执行这个计划" |
| `researcher` | 本技能的事实引擎 | 对话中出现可调研的未知 |

## 流程

### 1. 先建立上下文，再开口问

- 读项目的 AGENTS.md / README / 目录结构 / 相关模块现状——不要问用户文档里已写着的东西
- 需要深入现状（历史演进、跨模块依赖、某个机制怎么实现的）→ **派 `researcher` 只读调研**，拿带 file:line 的报告再继续
- 一次调研问题要自包含（researcher 没有我们的对话历史）

### 2. 澄清循环：一次一问

- **每条消息只问一个问题**。一个话题需要多问 → 拆成多条消息依次问
- **优先用 `AskUserQuestion` 出选择题**（带推荐项），开放式问题仅在选项列不全时用
- 聚焦三件事：**目的**（解决什么问题）、**约束**（不能动什么/必须兼容什么）、**成功标准**（怎么算做完）
- **未知分流**（关键纪律）：
  - 用户偏好/业务取舍 → 问用户
  - 事实/技术问题（库支不支持、现有代码怎么工作、业界怎么做）→ **派 `researcher`** 调研回来再继续，把结论和来源摆给用户看
  - 判断标准：**这个答案查得到吗？查得到就不问用户**

### 3. 探索方案

- 给出 **2-3 个方案**及各自取舍（复杂度/风险/工作量），**推荐项先行并说明理由**
- 对话式呈现，不甩大表格；用户对方案有异议 → 回到澄清循环

### 4. 分段呈现设计，逐段确认

- 你认为已理解需求后，开始呈现设计：**每段 200-300 字**，覆盖架构 / 组件划分 / 数据流 / 错误处理 / 测试策略
- **每段之后停下来问**："这部分看起来对吗？"——不对就回炉，不要闷头写完
- 用户在某段卡住 → 回到澄清循环或派 researcher 补证据

### 5. 设计定稿与出口

- 把逐段确认过的设计整理成文档，写入项目 `docs/plans/YYYY-MM-DD-<主题>-design.md`（写之前问用户要不要落盘；**不擅自 git commit**）
- 问用户："要继续进入实施吗？"
  - 要 → 需求现在已明确：进入计划模式出实施计划，或直接交给 `task-execute` 执行
  - 不要 → 到设计文档为止

## 关键原则

- **一次一问**：多条问题并出 = 用户漏答 = 白问
- **选择题优先**：`AskUserQuestion` 带选项和推荐，降低用户回答成本
- **事实先查再问**：能调研的未知派 researcher，问用户的只留偏好与取舍
- **YAGNI 无情砍**：每个设计里找一遍"现在不需要的功能"，砍掉并说明
- **必探索备选**：只有一个方案就没有取舍可言，永远给 2-3 个
- **增量确认**：设计分段呈现逐段过，不要一次性甩大文档
- **随时回炉**：任何一段不对就回到澄清，梳理不怕重来

## 反模式（出现即停手）

- 需求还没问清就开始写代码
- 一条消息里问三个问题
- 把"这个库支不支持 X"这类可调研问题抛给用户
- 只给一个方案不给备选
- 一次性甩出完整设计不给用户分段确认的机会
- 未经同意 git commit 或落盘到项目目录之外
- 调研结论不核对来源就转述给用户
