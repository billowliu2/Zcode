# 内联输出骨架（任务完成复核）

**默认不写文件**，直接输出到对话。用户明确要文件时才写 `TASK-REVIEW-<日期>.md`。

骨架只是示意，实际输出用 Markdown 正文。

---

## 总判

> 一句话：这次任务能不能交付。
>
> 只能取三个值之一 —— **可交付** / **需修正后交付** / **未完成**。
>
> 例：「6 条要求完成 5 条，`POST /orders` 的重试只加了超时没加重试逻辑（U2 部分实现），其余可用。**需修正后交付**。」

紧接着一两句说清最要紧的那一条，不要展开。

## 复核基准

```markdown
- 被复核的任务：<一句话，用户在什么时候提的什么要求>
- 审查集合：<工作区未提交 / commit A..B>，N 文件 / +X −Y 行
- 基准 commit：`<hash>`，工作区是否有未提交改动：是/否
- 自我背书风险：<若任务由我完成，写"本次复核由改动者本人执行，结论可信度低于第三方复核">
```

## 验证到什么程度

这一节必须诚实，是本 skill 的核心诚实条款。

| 层级 | 是否执行 | 命令 / 方式 | 结论 |
|---|---|---|---|
| 静态检查 | 是 | `npm run typecheck` | 通过 |
| 单元测试 | 否（未获用户同意 / 项目无此命令） | — | 未验证 |
| 端到端场景 | 否 | — | **未做端到端验证** |

明确写一句话总结停在哪个层级，例如：

> **仅静态检查通过，未做测试与端到端验证。** 因此"功能是否达到目的"只有代码级证据，没有运行级证据。

## 输出语气要求

- 总判直接给结论，不要"经过仔细复核"这类铺垫
- 漏做就说"U3 没做"，不要"U3 可能还需要补充一下"
- 没验证就说"未做端到端验证"，不要用"基本可用"模糊掉
- 不要为了显得工作量大而堆无关观察；用户要的是"做完没有、有没有坑"
- 篇幅服从信息量：全部达标且验证充分时，可以很短
