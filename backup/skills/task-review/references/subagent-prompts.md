# 六维度子代理 Prompt 模板（任务完成复核）

## 通用头部（每个 prompt 都要带）

```
你在为一次【任务完成复核】做只读取证。当前工作目录：<PWD>。

【背景】
  一批改动刚刚完成，主代理声称任务已完成，需要独立核实是否真的做到。
  你的结论会被主代理逐条核实，请只报告你实际取证到的事实。

【复现改动的方式 —— 你必须自己跑，不要等别人给你 diff】
  基准 commit：<hash>
  审查集合：<工作区未提交 / 暂存区 / commit A..B / 分支差异>
  复现命令：
    git diff HEAD              # 或 git show <hash> / git diff <A>..<B>
    git diff HEAD --name-status
    git diff HEAD --stat
  未跟踪文件：git status --porcelain 中 `??` 开头的项不在 diff 里，需直接读。

【用户对本任务提出的原始要求（逐条）】
  U1. <要求原文>
  U2. <要求原文>
  ...

【主代理声称完成的内容】
  <逐条摘录，不做修饰>

【你的审查维度】
  只负责 <T#>，其他维度由别的代理负责，不要越界。

硬性要求：
1. 只读。禁止 git add / commit / reset / checkout / stash / revert。
2. 禁止运行测试、构建、迁移、安装等有副作用的命令。
3. 每条结论必须能被你实际打开的 diff 片段或文件行证明，写出 `文件:行`。
4. 找不到问题就明确写"该维度未发现问题"，并列出你查过的位置与命令 —— 不要编一条凑数。
5. 搜索排除 node_modules / .venv / dist / build / target / .next / coverage / __pycache__ / vendor。
6. 不要复述整个 diff，不要写总结段，不要给鼓励性评价。
```

## 通用输出契约（每个 prompt 末尾附上）

```
输出格式（严格遵守）：

## 改动概况
共 N 文件，+X / -Y 行；列出改动文件清单（name-status）。

## 发现
每行一条，| 分隔：
严重度 | 文件:行 | 一句话问题 | 证据片段（≤3 行 diff 或代码） | 建议动作
严重度：P0 阻断 / P1 重要 / P2 一般 / P3 建议。按严重度降序。

## 该维度未发现问题的部分
- 你实际检查过但结论没问题的方面，每条一行，附检查位置或命令。

## 信息缺口
- 需要运行环境/数据/权限才能判断的点，说明缺什么。
```

**对你自己的重要提醒**：你没有运行环境，也没有用户的口头确认。凡是需要"实际跑一下才知道"的，一律写进"信息缺口"，不要猜测。

## T1 · 要求达成对账（本 skill 最关键的一路，建议单独派）

```
任务：【把用户原始要求逐条对账到代码实现】。

做法：
1. 取上面的 U1..Un 清单。若某些要求描述模糊，先把它翻译成 2–4 条**可观测的成功条件**。
   例：要求="加超时重试" → ①请求有超时上限 ②失败会重试且次数有限 ③重试耗尽后有明确错误返回。
2. 逐条到 diff 与相关文件里找实现证据。
3. 每条给一个状态，只能取：
   - 已实现      —— 找到实现，给 `文件:行`
   - 部分实现    —— 只满足了部分成功条件，指明缺哪条
   - 未实现      —— 按合理路径找过，没找到
   - 实现方式偏离 —— 做了，但和要求说的不一样，说明差异
   - 需更多信息  —— 依赖外部状态，无法判断
4. 特别注意这三种高发情形：
   - **做了别的**：改动实现了要求之外的事，而要求本身没做
   - **只做了一部分**：只加了超时没加重试；只改前端没改后端接口
   - **要求之间存在冲突**：满足了 U2 却违反了 U4（如"加功能"与"不动 public API"）

不要评价代码质量，不要提改进建议。你只负责对账：要求 → 有没有 → 在哪。
```

## T2 · 正确性

```
任务：【只看新增/修改的代码本身是否有缺陷】。按清单找**具体命中位置**：

1. 逻辑：条件方向反了、边界差一、循环终止条件错、默认值选错
2. 异步：漏 `await`、Promise 未处理、并发写同一状态、回调抛错无人接
3. 空值/类型：新增参数未校验、可选字段直接解构、`parseInt`/`JSON.parse` 未保护
4. 错误处理：新加的 catch 吞掉错误、只 log 不处理、catch 后当成功继续走
5. 资源：新增的连接/监听/定时器没有释放路径
6. 类型逃逸：新加的 `any` / `@ts-ignore` / `as` 断言掩盖了问题

只报你能指到行号的。不要评价"写得不够优雅"。
```

## T3 · 完整性（漏改）—— 价值次高，务必彻底

```
任务：【找漏改】。这批改动留下了一致性负债吗？逐项执行：

1. **符号级**：diff 中被改名的函数/类/类型/常量，旧名字在全仓还有没有引用？
   对每个被改符号名跑：
   grep -rn "<符号名>" . --exclude-dir={node_modules,.git,dist,build,target,.next,coverage,__pycache__,vendor}
2. **签名级**：函数增删改参数、改了返回结构 → 所有调用点是否同步更新？
   用符号名 grep 找调用点，不要只看 diff 里出现的文件。
3. **类型级**：改了 interface/type/protocol/字段 → 实现、序列化、反序列化、mock、
   测试 fixture 是否都跟着改？
4. **配置级**：新增配置项/环境变量/CLI 参数 → 有无默认值？`.env.example`、README、
   docker-compose、CI 配置里补了吗？
5. **契约级**：改了对外 API、导出符号、数据库字段 → 调用方/migration/文档同步了吗？
6. **删除级**：删除了导出/文件 → 全仓确认无人引用（含动态 import、字符串引用、配置中的路径）

输出区分两类：
- 【漏改】有明确证据说明某处需要改但没改 → 给 `文件:行`
- 【需确认】疑似相关但无法确定是否必须改 → 标 `?`

一条都没找到时，写"未发现漏改"，并列出你 grep 过的符号与路径清单。
```

## T4 · 副作用与回归

```
任务：【这批改动会不会破坏现有行为】。

1. 从 diff 提取所有**对外变化**：删除的导出、变化的签名、变化的默认值、
   变化的返回结构、变化的行为分支、删除的路由/字段/事件。
2. 逐个回答：谁依赖它？项目内还有谁在用？改动后这些调用方会怎样？
3. 关注"静默行为改变"：默认值变了但类型没变、返回值从 null 变 undefined、
   顺序变了、日志格式变了导致解析失败。
4. 关注"删除是否只是移动"：用 `git diff -M` 看重命名/移动检测，避免误判。
5. 涉及数据迁移的：可逆吗？失败后能恢复吗？

只报你能给出调用方证据或明确语义变化的。不要报"理论上可能有影响"。
```

## T5 · 一致性与规范（建议主代理自己做，见下方说明）

```
任务：【改动是否与项目既有惯例一致】。

1. 先读项目约定：AGENTS.md / README / CONTRIBUTING / 现有同类文件。
   以**项目实际做法**为准，不要用你的通用偏好。
2. 检查新代码是否偏离：包管理器与脚本命名、目录归属、命名惯例、
   错误处理/日志/返回值的既有模式。
3. 检查**注释与文档是否过期**：改了行为但注释/README 还是旧描述。

报告区分：
- 【不一致】有项目内既有范例证明应照它写 → 给两边 `文件:行`
- 【个人偏好】只是你觉得更好 → 不要报，或明确标 P3 偏好
```

## T6 · 验证与回滚

```
任务：【这次任务能验证吗？出问题能撤回吗？】

1. 测试：
   - 改动是否带了对应测试？`git diff HEAD --name-status` 里有没有测试文件？
   - 若无测试，同类文件旁边通常有 .spec/.test 吗？
   - 有无被 skip / 恒真 / 断言被注释掉的测试
2. 可验证性：
   - 从项目清单（package.json scripts / Makefile / pyproject / CI 配置）读出
     **真实存在**的验证命令。不存在的命令不要编。
   - 这次改动用现有命令能验证到什么程度？需要手工步骤的话说明是什么。
3. 回滚：
   - 能否安全 revert？有无不可逆部分（迁移、外部 API 调用、已发布契约、删除的数据）？
   - 是否需要 feature flag / 分批上线？

明确区分"没有测试"、"有测试但这次没更新"、"无法判断"。
注意：你**不允许运行**这些命令，只能读配置判断它们是否存在、是否覆盖本次改动。
```

## 派遣编排建议

| 任务规模 | 派遣方案 |
|---|---|
| ≤ 3 文件 / ≤150 行，无高风险面 | **不派**，主代理自己复核 |
| 4–8 文件 / 150–400 行，无高风险面 | 派 3 个：T1 / T3 / (T2+T4+T6 合并) |
| > 8 文件，或触碰任一高风险面 | 派 5 个：T1、T2、T3、T4、T6 |
| 用户提了 ≥4 条要求 | **T1 必须单独派**，避免主代理自己对账时漏条目 |
| monorepo 跨包 | 先按包分组，每组按上面规则派，总数 ≤ 8 |

**T1 必须单独一路** —— 它是本 skill 的核心，混在别处会被弱化。
**T3 建议单独一路** —— 需要大量 grep，混着做不彻底。
**T5 建议主代理自己做** —— 判断"是否符合项目惯例"要先理解项目，转述给子代理容易失真。

**所有派遣**：`subagent_type` 首选 `reviewer`（专职评审代理，只读 + 六维度 + 结构化报告）；不可用时退回 `Explore`。ZCode 的 Agent 工具没有 model 参数；禁止把主代理自身作为子代理。
