# 任务完成复核（Task Review）

用在**任务收尾、交付之前**。核心动作只有一件：

> 把「我刚才声称完成的事」和「代码里实际发生的事」并排放在一起，逐条核对。

这个 skill 存在的理由很具体：任务执行末尾是最容易出错的一刻 —— 前面改了半天，收尾时凭记忆写一句"已完成"，而实际漏了某个分支、漏了调用方、漏了用户在第 2 条里提的要求。**验收不是重新检查代码质量，是检查"我说的话"和"代码"是否一致。**

## 与既有 skill 的边界（先确认没串台）

| Skill / 机制 | 审的对象 | 触发语 | 产出 |
|---|---|---|---|
| **`task-review`（本 skill）** | **一次任务的完成情况**（声称 vs 事实） | "复核一下刚才改的""真的做完了吗" | 内联汇总 |
| ZCode 计划模式（EnterPlanMode） | 需求 → 方案（更上游） | "我想加个 X 怎么做""调研一下 Y 可不可行" | 计划文档 |
| `task-execute` | **执行**任务（本 skill 的上游） | "执行这个计划""按方案落地" | 交付总结 |

分工要点：
- 本 skill 的输入是**一个已完成（或声称已完成）的任务**，判据是**用户原始要求 + 自己的完成声明**
- 上游衔接：`task-execute` 第 5 步会主动调用本 skill 做完成复核；从那边进来时，Stage 0 的"用户原始要求"直接取它的任务拆解清单
- 若上游走的是计划模式，其计划文档里的「实施步骤」就是本 skill 的对账基准
- 发现需要全项目体检的线索 → 只在结论里提一句，不越界执行
- 若复核中发现我的完成声明本身有系统性偏差（反复把"未验证"写成"已完成"），在结论里明确标出该偏差，并建议用户换新会话或第三方复核

## 铁律

1. **先列出"我声称完成了什么"，再去看代码**。顺序反了会变成"我看到代码觉得还行"，那是自我背书，不是验收。
2. **回验用户原始要求的每一条**。用户一次提 5 条要求，只做了 4 条是最常见的失败。逐条对账，不许合并成一句"按需求完成"。
3. **漏改是首要风险**。改了签名没改调用方、改了类型没改实现、加了配置没加默认值 —— 必须全仓搜索受影响位置，不能只看 diff 里出现的文件。
4. **"能编译/能跑"不等于"做完了"**。必须真正执行用户场景，不是只 import 试试。
5. **未验证的事必须说"未验证"**。这是本 skill 最重要的一条：宁可承认没做端到端验证，也不能把未验证写成已完成。
6. **复核阶段不改代码**。发现问题先报告，由用户决定修不修。
7. **结论必须带 `file:line` 或命令输出**。说不出位置的问题不写。

## 流程

### Stage 0 · 提取完成声明（主代理，先写下来再动手）

**在打开任何代码之前**，把本次任务的完成情况写成一张清单。这是整个复核的对照基准，写晚了就会被代码带偏。

来源三处，全部提取：

1. **用户原始要求**（最重要）—— 回到对话开头，把用户提的每一条要求拆成独立条目。用户说"帮忙加个超时重试，记得更新文档，别动 public API"，这是 3 条。
2. **我给出的完成声明** —— 上一轮回复里我说的"已完成/已修复/已添加"逐句摘出。
3. **代码里实际做的** —— 暂不填，Stage 2 再取证。

**若被复核任务是 swarm 工作流批次产出**：完成声明取批次报告的逐项结论，对账基准是 `items` 逐条 + `prompt_template` 里写的完成判据（模板没写判据的，这本身就是发现）。批次报告属于"声称"侧材料——逐项仍须按 Stage 2 用 `git diff` / 读代码独立取证，不能因为报告写着"已完成"就采信。

产出格式：

```
ID | 类型 | 内容 | 我的声明 | 实际状态
R1 | 用户要求 | 给 fetch 加超时 | 已加 | 待核
R2 | 用户要求 | 加 3 次重试 | 已加 | 待核
R3 | 用户要求 | 更新文档 | 已更新 | 待核
R4 | 用户要求 | 不动 public API | 未提 | 待核   ← 我根本没提这条
```

第 4 类要给特别警惕：**用户提了但我完全没在声明里提及的**，往往就是漏做的。

若任务是我自己在上一轮做的，必须显式写下：

> 「本次复核带有自我背书风险 —— 改动由我完成，我来验收。结论可信度低于第三方复核。」

这句话要出现在最终输出里，不能只在心里想。

### Stage 1 · 确定改动范围（取证，不凭记忆）

```bash
git rev-parse --short HEAD && git branch --show-current
git status --porcelain=v1
git diff --stat                     # 未暂存
git diff --cached --stat            # 已暂存
git log --oneline @{u}..HEAD 2>/dev/null   # 未推送
git stash list
```

按任务形态选定集合，并在报告里写明审的是哪一个：

| 情况 | 命令 |
|---|---|
| 改完还没提交（最常见） | `git diff HEAD` |
| 已提交几次 | `git log --oneline -10` 确认区间 → `git diff A..B` |
| 相对主干 | `git diff main...HEAD` |

**必须处理的边界情况**：

- 工作区干净、也没有本次任务的提交 → 要么任务提交了（找 commit），要么**我根本没做出实际改动**。后者是重要发现，要直说。
- 有未跟踪文件（`??`）→ **单独列出**。新增文件未 `git add` 时不存在于任何 diff 里，是"看起来改动很小"的常见假象
- 有 `git stash` → 提示可能存在被遗漏的改动
- 合并/rebase 进行中 → 停止，先处理冲突
- 跨多个包（monorepo）→ 按包分组统计

量化：

```bash
git diff HEAD --numstat | awk '{a+=$1; d+=$2} END {print "added",a,"deleted",d}'
git diff HEAD --name-status   # A/M/D/R，识别删除与重命名
```

### Stage 2 · 分流：主代理复核 or 派子代理

用户明确要求：**任务大或改动多时不要用主代理/主代理模型来审，派子代理专项复核后汇总**。

| 条件 | 处置 |
|---|---|
| ≤ 3 文件 且 ≤ 150 行 且 无高风险面 | 主代理复核 |
| 4–8 文件 或 150–400 行 | 主代理可做；**触碰任一高风险面 → 必须派** |
| > 8 文件 或 > 400 行 或 跨 3 个以上模块 | **必须派子代理** |
| 用户明说"改动较多 / 项目较大" | **必须派**，忽略量化阈值 |
| 任务涉及用户多条要求（≥4 条） | 建议派 R1 一路专做"要求逐条对账"，避免我自己漏 |
| **复核对象是多个独立单元的批量改动**（monorepo 跨包、多服务、N 个独立模块/文件） | 可用 **swarm 工作流**做同构批量取证：`read_only: true`，每个单元一条 item，模板写明只读审查纪律与取证要求（结论带 file:line）；Stage 5 的逐条核实规则不变 |

> swarm 批量取证是"按单元派"的合法场景，不违反"按维度派，不按文件派"——后者针对的是**单个任务**的复核切分；批量取证之后，跨单元的横向问题（接缝、重复实现）仍由主代理统一把关。

**高风险面**（触碰任一即升级派子代理，与行数无关）：数据库 schema/迁移、鉴权与权限、支付与金额、数据删除或批量更新、对外 API 契约、构建配置与 CI、依赖清单、并发与事务、全局状态与中间件。

**派遣规则**（与既有护栏一致，不得违反）：

- 子代理类型首选 `reviewer`（专职评审代理：只读、按六维度取证、输出带证据的结构化报告，定义在 `~/.zcode/agents/reviewer.md`）；`reviewer` 不可用时（如旧会话未加载）退回 `Explore`
- **不得把主代理自身作为子代理**；ZCode 的 Agent 工具没有 model 参数，派遣只读复核时不要用全工具类型
- **按维度派，不按文件派** —— 按文件切分会让跨文件的漏改问题被切开，谁都看不见
- 并发 3–5 个，超过就合并
- **子代理自己跑 `git diff` 取原文**，不要把大段 diff 粘进 prompt（既截断又失真）。给它：复现命令 + 用户原始要求 + 关注点，**不给我的结论**
- 子代理禁止 `git add/commit/reset/checkout/stash`，禁止跑测试与构建

维度定义与 prompt 模板见 `references/subagent-prompts.md`。

### Stage 3 · 六维度复核

| 维度 | 核心问题 | 典型命中 |
|---|---|---|
| **T1 要求达成** | 用户提的每一条都做了吗？有没有做了别的、漏了原本的？ | 5 条要求只做了 4 条 |
| **T2 正确性** | 新写的逻辑对不对？边界、空值、异常、并发 | 差一错误、漏 `await`、catch 吞错 |
| **T3 完整性（漏改）** | 该跟着改的地方都改了吗？ | 改签名没改调用方、加配置没加默认值 |
| **T4 副作用与回归** | 会不会破坏现有行为/现有调用方？ | 默认值变化、返回结构变化、删了有外部依赖的导出 |
| **T5 一致性与规范** | 与项目既有惯例、AGENTS.md 约定一致吗？ | 项目用 pnpm 却写 npm 脚本、命名断裂、注释过期 |
| **T6 验证与回滚** | 有测试吗？能验证吗？出问题能撤回吗？ | 无测试、迁移不可逆、无回滚方案 |

**T1 的做法（本 skill 的重点）**：

对 Stage 0 清单的每一条，逐条取证：

- 找到实现 → 给 `file:line`，标"已实现"
- 找不到 → 标"**未实现**"，这是最重要的发现
- 实现了但方式和要求不同 → 标"**实现方式偏离**"，说明偏离在哪
- 我声明里说做了但代码里没有 → 标"**声明与事实不符**"，这是最严重的一类

**T3 漏改的具体查法**：

```bash
# 被改名的符号 → 全仓找旧名字与所有调用点
git diff HEAD --name-only
grep -rn "<被改的符号名>" . --exclude-dir={node_modules,.git,dist,build,target,.next,coverage,__pycache__,vendor}

# 新增的环境变量/配置项 → 确认有默认值与文档
grep -rn "<新变量名>" . --exclude-dir={node_modules,.git,dist,build}
```

对每个被修改的导出符号问："谁在用？它们需要跟着改吗？"

**T4 的具体查法**：

```bash
# 被删除的标识符是否在别处仍被引用
git diff HEAD -U0 | grep '^-' | grep -oE '[A-Za-z_][A-Za-z0-9_]{3,}' | sort -u
# 对外导出签名是否变化（先看无 .d.ts 变化但实现变了的情况）
git diff -M -U3 -- <public entry files>
```

### Stage 4 · 端到端验证（决定"是否真的完成"）

**这是与其他 review 最大的区别**：任务复核必须尝试真正跑起来，而不是只读代码。

分三步，难度递增：

1. **静态可行**：`typecheck` / `lint` 通过 → 只能证明"没有语法级错误"，**不能证明功能对了**
2. **测试通过**：跑项目真实存在的测试命令 → 证明"没有回归"，仍不能证明新功能对
3. **场景复现**：按用户描述的场景实际调用一遍 → 这才是"达到目的"的证据

第 3 步做不了时，必须明确写："**未做端到端验证，仅静态检查通过。**" —— 这是本 skill 的核心诚实条款。

**跑命令前先确认两件事**：

- 命令真实存在：从 `package.json scripts` / `Makefile` / `pyproject` / CI 配置里读，**不要凭印象写 `npm test`**
- 有无副作用：`npm test` 一般安全；`install` / `build` / `migrate` / `seed` 可能写产物或改数据 → **先问用户**

### Stage 5 · 逐条核实子代理的结论（派了子代理才需要）

子代理交回的是**线索**，不是判决。每条"有问题"的结论，主代理必须亲自确认：

1. `Read` 打开被引用的文件与行，确认与指控相符
2. 跑只读命令交叉验证（`grep` / `git log -S` / `git blame`）
3. 对"漏改"类指控，**自己再搜一遍** —— 子代理漏搜是高频误报源

三档标注，必须出现在输出里：

- `A 已核实`：我亲自读到该行或看到命令输出
- `B 旁证`：强证据但未运行验证 → 措辞必须是"基于 X 推断"
- `C 无法核实`：需要运行环境/数据 → **不能用来否定改动**，只能标"存疑"

**任务复核专属的核实陷阱**：

- **行号来自 diff，不是文件行号** → 下结论前必须落到真实文件行，`Read` 带 `line_offset`
- **diff 上下文太短** → 用 `git diff -U10` 补足，很多"缺少判断"实际在上文已判过
- **只看 diff 不看文件全貌** → 函数可能被 `try` 包着、类可能继承了基类实现
- **删除行不等于删除功能** → 用 `git diff -M` 识别移动/重命名
- **未跟踪的新文件不在 diff 里** → 必须单独读
- **我自己的记忆偏差** → 复核前 `git status` 确认当前状态，不要凭"我记得改了"

### Stage 6 · 内联输出

默认内联输出，**不写文件**。用户明确要文件时才写 `TASK-REVIEW-<日期>.md`。

结构见 `references/report-format.md`。硬要求：

- **开头一句话总判**：这次任务能不能交付（可交付 / 需修正后交付 / 未完成）
- **对照表**：用户要求 ← → 实现 ← → 状态，一眼看完
- **声明与事实不符的条目单列**（哪怕只有一条，也必须单列）
- **漏改清单**：即使为空也写"未发现漏改"
- **验证到什么程度**：静态 / 测试 / 端到端，现在停在哪一步
- **未核实的部分**：明说
- 建议分"必须改"和"建议改"两档

## 建议的质量标准

每条建议必须能直接执行：

1. **具体动作**（动词开头，指明文件与行）
2. **理由**（不改会怎样）
3. **验证方式**（用项目里真实存在的命令）

- ✗ "建议加强错误处理"
- ✓ "`src/api/client.ts:88` 的 fetch 没有超时，网络抖动时 `request()` 会永久挂起。加 `AbortSignal.timeout(5000)`，用 `npm test -- client.spec.ts` 验证现有用例不回归"

## 反模式（出现即停手）

- **收尾时不看代码，凭记忆说"已完成"** —— 本 skill 要防的头号问题
- 把用户的多条要求合并成一句"按需求实现"，不做逐条对账
- 用户提了但我的声明里完全没提的条目（通常就是漏做的）被忽略
- 只读 diff 不看被改文件的完整上下文，得出"缺少 X"的误判
- 只看 diff 里出现过的文件，不去搜被改符号的**其他**调用方
- 忽略未跟踪的新文件
- 只跑 typecheck 就说"验证通过"
- 把"未做端到端验证"写成"已完成"
- 任务很大却由主代理直接复核（违反用户明确要求）
- 子代理 prompt 里塞自己的结论，诱导确认
- 未经同意跑 install/build/migrate
- 复核阶段顺手改代码

## 交付前自检

- [ ] 用户原始要求已拆成独立条目，逐条给了状态（不是笼统一句"已完成"）
- [ ] "声明与事实不符"的条目已单列（没有就写"无"）
- [ ] 走完 T1–T6 六维，不适用的写明"不适用"
- [ ] "漏改清单"节存在（哪怕内容是"未发现"）
- [ ] 验证程度已明确标注（静态 / 测试 / 端到端，停在哪一步）
- [ ] 涉及高风险面或大改动时，确实派了子代理（或说明为何没派）
- [ ] 派了子代理时，`subagent_type` 首选 `reviewer`（只读评审专用），未用全工具类型
- [ ] 每条问题都能指到 `file:line` 或命令输出，且我亲自读过
- [ ] 自我背书风险已声明（若任务是我做的）
- [ ] 没跑未获同意的命令，没改任何文件
- [ ] 总判明确：可交付 / 需修正后交付 / 未完成
