# 任务编排执行（Task Execute）

拿到一个任务或计划，按「**先审计划 → 再编排 → 派子代理执行 → 逐个验收 → 整体把关**」推进。

主代理的核心职责是**编排与验收**，不是自己把所有活干完。凡是能独立成块、可并行、上下文体量大的子任务，都应该派出去；主代理只保留编排、核实、整合这三件必须集中做的事。

## 与相邻 skill 的边界

| Skill / 机制 | 定位 | 何时用 |
|---|---|---|
| **`task-execute`（本 skill）** | 把任务**做出来** | "执行这个计划""按方案落地" |
| ZCode 计划模式（EnterPlanMode） | 只有需求、**还没有计划**时先理清并给建议 | "我想加个 X 怎么做""调研一下 Y 可不可行" |
| `task-review` | 做完后**复核声称 vs 事实** | "复核一下刚才改的""真的做完了吗" |

`task-execute` 的第 5 步天然衔接到 `task-review`：执行完毕后主动走一遍完成复核，而不是自己说"已完成"就算完。这是本 skill 与其他编排流程最大的区别。

**上游衔接**：如果用户只有需求、还没形成计划，先进入计划模式（EnterPlanMode）把目的与约束理清，确认后再回到本 skill 执行。反之，用户已给出明确计划 → 直接用本 skill，不要绕道计划模式再问一遍。

## 用户提供的输入

`$ARGUMENTS`

按下面第 0 步判断它属于哪种情况：完整计划 / 粗略计划 / 只有目标。

---

## 第 0 步 · 先审计划，不完整就补

**不要拿到计划就开干。** 先把计划放到桌上检查，这一步省掉，后面必然返工。

### 0.1 完整性检查

逐项确认是否存在，缺失就标出来：

| 要素 | 缺失时的后果 |
|---|---|
| 目标 | 做完了也不知道算不算成功 |
| 范围（做什么 / 不做什么） | 越界改动、扩大爆炸半径 |
| 步骤拆解 | 无法并行，也无法估算 |
| 验收标准 | 第 4 步无从判定 |
| 依赖与前置条件 | 中途卡死 |
| 风险与回滚 | 出问题无法收场 |

### 0.2 正确性检查

- 技术路线在当前项目里**可行吗**？（先看项目实际用了什么，不要假设）
- 与现有代码/架构/约定**冲突吗**？
- 有没有和项目既有能力重复造轮子？
- 步骤之间的**顺序**对不对？有没有把依赖方排在依赖前面？
- 有没有**不可逆**动作（删数据、改 schema、改对外契约）被轻描淡写地放在中间步骤？

检查时以**项目实际事实**为准：读 `AGENTS.md` / `README.md` / 依赖清单 / 目录结构，不要凭通用经验下判断。

### 0.3 补全与确认

- **计划完整** → 简述你的理解，直接进入第 1 步
- **计划有缺口** → 先补全，然后用简短清单告诉用户「**补充/修正了什么、为什么**」，再进入第 1 步
- **只有目标没有计划** → 起草一份（目标 / 拆解 / 验收标准 / 风险），**确认后再执行**
- **计划根本性错误** → 停下来说明问题，给出替代方案。不要默默按错的计划做

> 注意：补全不等于擅自扩大范围。补的是"计划本身欠缺的要素"，不是"我觉得还应该多做点什么"。

## 第 1 步 · 编排

把任务拆成可执行单元，为每个单元定好三件事：

| 项 | 要求 |
|---|---|
| **验收标准** | 可判定，不是"做好了"而是"`npm test` 通过"或"`file:line` 处有 X" |
| **输入** | 子代理需要的全部上下文：路径、现状、约束。子代理是零上下文的，它不知道我们前面聊了什么 |
| **依赖** | 依赖谁、被谁依赖。无依赖的并行，有依赖的串行 |

**拆解粒度**：一个子任务应当能用一段自包含的 prompt 说清楚，且产出可独立验收。太细会导致派遣开销大于收益，太粗则无法并行也无法定位失败。

**子代理类型选择**（ZCode 的 Agent 工具通过 `subagent_type` 指定类型）：

| subagent_type | 适用 | 工具 |
|---|---|---|
| `coder` | **落地实现首选**：全栈实现（前端/后端/数据库/契约联调）、写代码、修 bug、跑测试验证（专用实现代理，定义在 `~/.zcode/agents/coder.md`） | 全工具 |
| `researcher` | **综合调研**：本地检索 + git 考古 + 网络搜索三路取证，输出带来源的调研报告；带诚实条款（不臆测、未查明如实标注，定义在 `~/.zcode/agents/researcher.md`） | 全工具（纪律约束源项目零修改） |
| `Explore` | 只读**定位**：广撒网找文件/找代码位置/验证现状，不负责综合调研报告 | 只读工具 |
| `reviewer` | 改动复核与批量取证（专职评审，定义在 `~/.zcode/agents/reviewer.md`） | Read+Bash 只读 |
| `general-purpose` | 兜底：`coder` 不可用时（如旧会话未加载）替代它做实现 | 全工具 |

> 调研类派遣的分工：**找位置/验证存在性 → Explore；查清来龙去脉并要汇总报告 → researcher**。researcher 的结论仍属"声称"侧——关键结论主代理须按第 3 步抽验来源。

**编排路由：逐个派遣 Agent，还是走 swarm 工作流**（按拆解结果的形态动态决定）：

| 拆解形态 | 路由 | 理由 |
|---|---|---|
| **同构批量**：≥3 个结构相同的独立子任务（同一套指令 + 各自差异部分，互不依赖互不重叠） | **swarm 工作流**（`CreateWorkflow` 的 `saved: {name: "swarm", args}`） | 模板写一次、逐项并行、统一汇总；典型如"为 N 个模块分别补测试""批量审查 N 个文件""批量调研 N 个问题" |
| **异构任务图**：子任务形态各异（调研/实现/审查混合），或有依赖链 | 逐个 `Agent` 派遣（本 skill 的常规路径） | 形态不同写不成一个模板；有依赖的子任务禁止并行 |
| 混合：计划里既有异构部分又有同构批量部分 | 异构部分 Agent 派遣，同构批量部分一次 swarm | 两条路径不冲突，按块分流 |
| 同构但只有 2 项，或批次内子任务有依赖 | 不走 swarm，直接并行 `Agent` 调用 | 并行收益小于工作流开销 / 有依赖禁止并行 |

走 swarm 时的参数构造：`prompt_template` 用 `{{item}}` 占位符写共享指令（含输入、预期输出、完成判据），`items` 列差异部分，公共背景进 `shared_context`，只读批次加 `read_only: true`；拆分没把握先 `dry_run: true` 预览展开后的每条 prompt。

## 第 2 步 · 派遣

### 硬性约束

- **类型必须匹配任务**：落地实现一律首选 `coder`（它自带先读后改、找调用方、验证、安全护栏的实现纪律）；只读取证与方案调研用 `Explore`（只读，天然改不了文件）；`coder` 不可用时才退回 `general-purpose`。ZCode 的 Agent 工具没有 model 参数，不要臆造
- **不得把主代理自身作为子代理**，也不得让子代理反过来调度主代理
- 子代理 prompt **必须自包含**：它没有我们的对话历史

### prompt 要素

每个子任务 prompt 至少包含：

```
目标：<这个子任务要达成什么>
背景：<项目路径、技术栈、相关现状 —— 它不知道的事情全要写>
已知事实：<我已经查到的，避免它重复劳动>
约束：<不能做什么、必须遵守什么>
交付：<输出什么、写到哪、什么格式>
验收：<怎么算完成>
```

### 并行与串行

- 无依赖子任务 → 同一响应里多个并行 `Agent` 调用；**同构批量（见第 1 步路由表）→ 改走 swarm 工作流**，不要手写 N 个相同结构的 Agent 调用
- 有依赖 → 前序完成、验收通过后再派后序（swarm 批次内同样禁止有依赖的条目）
- 子代理类型各异、prompt 差异大 → 用多个独立 `Agent` 调用，不要硬塞进一个 swarm 模板

### 上下文卫生

派出去的子任务，**主代理不要同时自己做一遍**。重复劳动既浪费，又会产生两套结论需要调和。派出后主代理去做别的事，或等待结果。

## 第 3 步 · 逐个子任务验收

子代理返回的是**产出**，不是**结论**。每个返回都要验收，不能直接采信：

- [ ] **达到验收标准**了吗？逐条对照第 1 步定的标准，不是"看起来还行"
- [ ] **真的改了**吗？`git status` / `git diff` 确认，别只看它的文字汇报
- [ ] 有没有**未完成、占位、TODO、被注释掉的代码**？
- [ ] 有没有**引入新问题**？（顺手改了不该改的、删了不该删的）
- [ ] 涉及测试的，**建议实际跑一下** —— 跑之前确认命令真实存在于项目清单里，且征得用户同意
- [ ] 它汇报的 `file:line` **真的对应**吗？抽验几处

**验收不通过怎么办**：

1. 优先 `SendMessage` 继续同一子代理（它保留着自己的上下文，修正成本低）；swarm 批次里的不达标条目同理——用 `followups: [{index, followup}]` 追问，该条目沿用原子代理上下文
2. 问题严重或原方向错了 → 重新派遣，prompt 里说明上次错在哪（swarm 场景则等批次结束，对该条目单独派 `Agent` 深入处理）
3. 连续两次修不好 → 停下，把问题摆给用户，不要无限重试烧额度

## 第 4 步 · 整体把关

所有子任务完成后，站在整体视角再核一遍：

- **完整度**：对照最初计划的每一步，有没有漏做的？用户提的每一条要求都覆盖了吗？
- **正确性**：各部分拼起来**自洽**吗？接口对得上吗？有没有两个子代理对同一处做了冲突的改动？
- **一致性**：命名、风格、架构归属是否统一？跨子任务的重复实现要不要合并？
- **副作用**：有没有超出原计划范围的改动？

这一步最容易漏的是**跨子任务的接缝**：每个子任务单独看都对，拼起来不对。重点检查接口、共享类型、配置项。

## 第 5 步 · 完成复核（衔接 task-review）

在说"已完成"之前，**主动走一遍复核**：

- 若改动较大（> 8 文件 / > 400 行 / 触碰高风险面）→ 调用 `task-review` skill 做完整复核，必要时派子代理专项审
- 若改动小 → 至少自己对照"用户原始要求逐条 → 实际实现"做一遍对账

**明确禁止**：不经验证就输出"全部完成"。验证到了哪一层（静态 / 测试 / 端到端）必须说清楚，未做端到端验证就明说。

## 第 6 步 · 交付总结

向用户汇报，结构：

1. **做了什么** —— 对照计划的每一步，完成/未完成
2. **验证到什么程度** —— 静态检查 / 测试 / 端到端，具体命令与结果
3. **改动清单** —— 哪些文件，大致范围
4. **未完成 / 阻塞项** —— 有什么没做，为什么，需要用户提供什么
5. **遗留风险与建议** —— 后续该注意什么

不要只报喜。没做到的、没验证的，必须出现在总结里。

## 兜底规则

- **遇阻**：先自己尝试解决（换路径、查文档）；解决不了就明确告知阻塞点 + 需要用户提供什么，不要静默降级
- **不擅自做变更性操作**：`git commit` / `push` / 删除 / 迁移，未经用户同意不做
- **不做超出计划范围的"顺手优化"**：发现了就记下来在交付总结里提，不擅自改
- **不无限重试**：同一子任务两次修正仍不达标，升级给用户

## 反模式（出现即停手）

- 拿到计划不看完整性就直接开干
- 主代理自己把活全干了，子代理只是摆设（或反过来，主代理完全不做核实）
- 子代理 prompt 写成"把 X 做好"，没有具体路径与验收标准
- 子代理返回后不验收，直接采信其"已完成"
- 派出去后主代理又自己做一遍同一件事
- 各子任务孤立看都对，但没检查跨任务的接缝（接口/共享类型/配置）
- 未验证就说"全部完成"
- 改文件的任务派给了只读的 `Explore`；实现类子任务绕过 `coder` 直接派 `general-purpose`（除非 `coder` 不可用）
- 连续重试烧额度而不上报阻塞

## 交付前自检

- [ ] 计划经过完整性与正确性检查，缺口已补并告知用户
- [ ] 每个子任务都有明确的验收标准和自包含的 prompt
- [ ] 每次派遣都选对了 `subagent_type`（实现首选 `coder`，只读用 `Explore`，`general-purpose` 仅兜底）
- [ ] 同构批量子任务（≥3 项同模板独立任务）走了 swarm 工作流，或说明了为何没走
- [ ] 每个子代理的产出都已验收（含实际 `git diff` 核对）
- [ ] 检查过跨子任务的接缝（接口、共享类型、配置）
- [ ] 对照用户原始要求逐条核过覆盖情况
- [ ] 验证程度已标注（静态 / 测试 / 端到端），未验证的已明说
- [ ] 交付总结包含未完成项与遗留风险，不只报喜
- [ ] 未擅自执行 commit / push / 删除 / 迁移
