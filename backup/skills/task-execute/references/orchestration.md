# 编排参考：拆解、派遣、验收

## 一、怎么拆才合理

### 拆解的三个判据

一个子任务合格的标准是三条**同时**满足：

1. **可自包含描述** —— 一段 prompt 能说清，不需要子代理追问
2. **可独立验收** —— 有明确的判定标准，不依赖其他子任务的结果才能判断
3. **有实际收益** —— 单独派出比主代理直接做更划算（上下文体量大、可并行、需要专门技能）

三条缺一就不该拆出去。常见的过度拆解：把"改 3 个文件的 import"拆成 3 个子任务 —— 派遣开销远大于收益。

### 按什么维度拆

| 任务形态 | 拆解维度 | 注意 |
|---|---|---|
| 多模块独立改造 | 按模块 | 检查模块间接口是否要同步改 |
| 一个功能的前后端 | 按层 | 必须约定接口契约，否则拼不上 |
| 大范围调研 | 按问题域 | 各域结果要能合并 |
| 重构 + 测试 | 按"改"与"验" | 验的一方要独立于改的一方 |
| 文档更新 | 按文档单元 | 需先确定统一的术语与结论 |

**反模式**：按文件数平均分配。文件之间有依赖，平均分配会让子代理互相等或互相冲突。

### 依赖图

拆完先画依赖（心里画即可）：

```
A ──→ C
B ──→ C
      C ──→ D
```

- 同层（A、B）并行
- 跨层（C 依赖 A、B）串行，且**必须验收通过**再进下一层
- 出现环 → 拆解有问题，重新划边界

## 二、子代理 prompt 模板

### 通用骨架

```
【目标】
<一句话：这个子任务要达成什么>

【背景】
- 项目路径：<绝对路径>
- 技术栈：<语言/框架/包管理器>
- 相关现状：<已有的文件、已实现的部分、已知的坑>

【已知事实】（我已经查到的，你不用重复调查）
- <file:line 处的实现是 ...>
- <项目使用 X 而非 Y>
- <已确认 Z 不存在>

【要做的事】
1. <具体动作，指明文件>
2. ...

【约束】
- 只改 <范围>，不要动 <其他>
- 遵循项目既有惯例：<举例>
- 不要执行 git commit / push / 迁移

【交付】
- 改动的文件清单
- 关键改动的 file:line
- 验收自检结果

【验收标准】
- <可判定条件 1>
- <可判定条件 2>
```

### 按类型的变体（subagent_type：`coder` 实现首选 / `Explore` 只读 / `general-purpose` 兜底）

**Explore（只读调查）**

```
【目标】查清 <问题>
【范围】<目录>，排除 node_modules/dist/build 等
【要回答】
  1. <问题 1>
  2. <问题 2>
【交付】每条结论带 file:line；找不到就写"未找到"，并列出搜过的路径
【禁止】修改任何文件
```

**Explore（只读方案设计）**

```
【目标】为 <需求> 出实施方案
【约束】<技术栈、兼容性要求、不能引入新依赖>
【要产出】
  1. 推荐的方案与理由
  2. 被否决的备选方案及否决原因
  3. 涉及的文件清单（真实路径）
  4. 分步实施顺序与依赖
  5. 风险点
【禁止】开始改代码
```

**coder（实施，首选；`coder` 不可用时用 `general-purpose` 兜底，模板相同）**

```
【目标】实现 <功能>
【已知】<关键文件与现状>
【要做】
  1. 在 <file> 中 <动作>
  2. 同步更新 <调用方 / 类型 / 测试>
【约束】
  - 不要改 <无关部分>
  - 遵循 <项目惯例>
  - 不要 git commit/push
【验收】
  - <命令> 通过
  - <file:line> 处体现 <预期行为>
【交付】改动清单 + 自检结果 + 未完成项（如有）
```

### prompt 的常见缺陷

| 缺陷 | 后果 | 修法 |
|---|---|---|
| "把 X 做好" | 子代理自由发挥，产出不可控 | 写成具体动作 + 文件路径 |
| 没给路径 | 子代理到处找或找错 | 给出绝对路径或明确相对路径 |
| 没给验收标准 | 无法判断是否完成 | 写成可判定条件 |
| 塞了自己的结论 | 诱导确认 | 只给事实，不给判断 |
| 大段粘贴文件内容 | 截断、失真 | 给路径让它自己读 |
| 一次派太多 | 每个都做不深 | 拆到粒度合理为止 |

## 三、验收清单

每个子代理返回后逐项过：

### 硬性核对

- [ ] `git status` / `git diff` 确认**真的改了**，不是只在文字里声称
- [ ] 改动文件清单与预期一致，**没有多改**
- [ ] 汇报的 `file:line` 抽验 2–3 处，**确实对应**
- [ ] 无占位内容（TODO / `...` / "此处略" / 空函数体）
- [ ] 无被注释掉的代码、无调试残留（`console.log` / `print` / `debugger`）

### 质量核对

- [ ] 达到第 1 步定的验收标准（逐条对照，不凭印象）
- [ ] 没有引入新问题（顺手改了不该改的、删了在用的）
- [ ] 与项目惯例一致
- [ ] 相关调用方/类型/文档已同步（这是最常见的漏改）

### 验证

- [ ] 有测试的，**征得用户同意后**跑测试
- [ ] 命令必须真实存在于项目清单（`package.json scripts` / `Makefile` / `pyproject` / CI 配置）
- [ ] 未跑验证的，明确记为"未验证"，不得算作通过

### 不通过时的处置

| 情况 | 处置 |
|---|---|
| 小偏差（命名、格式、漏改了次要处） | `SendMessage` 继续同一子代理修正 |
| 方向对但做得不完整 | `SendMessage` 继续，明确指出缺哪几项 |
| 方向错了 | 重新派遣，prompt 里说明上次错在哪 |
| 两次修正仍不达标 | 停止重试，把问题交给用户 |

## 四、跨子任务接缝检查

所有子任务完成后，**必查**这些接缝（每个子任务单独看都对，拼起来不对的高发地）：

- **接口**：调用方与被调用方的签名/返回结构一致吗？
- **共享类型**：两个子代理是否各自定义了本该共用的类型？
- **配置项**：新增配置有默认值吗？`.env.example` / 文档补了吗？
- **重复实现**：有没有两个子任务写了同一个工具函数？
- **冲突改动**：有没有两个子代理改了同一处，后者覆盖了前者？
- **风格**：命名与结构是否统一？

快速查法：

```bash
git status --porcelain
git diff --stat
grep -rn "<新增的公共符号>" . --exclude-dir=node_modules --exclude-dir=.git
```

## 五、上下文卫生

- **派出后不要再自己做一遍** —— 重复劳动且产生两套结论
- **子代理的中间过程不进主代理上下文** —— 这正是派遣的价值所在
- **但结论必须进** —— 验收与接缝检查依赖它们
- **并行数量控制在 3–6 个** —— 超过后验收成本会超过并行收益

## 六、同构批量：swarm 工作流路由

拆解完成后先判断形态，再选路径（对应 SKILL.md 第 1 步的路由表）：

**判定为同构批量**（≥3 项、同一套指令可模板化、相互独立互不重叠）时，不要手写 N 个相同结构的 `Agent` 调用，改用 swarm 工作流：

```
CreateWorkflow(saved: { name: "swarm", args: {
  items: ["<子任务1差异部分>", "<子任务2差异部分>", ...],
  prompt_template: "<共享指令，含 {{item}} 占位符、输入、预期输出、完成判据>",
  shared_context: "<所有条目都需要的背景：项目约定、文件清单>",
  label: "<批次标签>",
  read_only: <只读批次 true，实现批次 false>,
} })
```

要点：

- **验收标准写进模板**：swarm 的逐项结果就是验收对象，完成判据不在模板里就没法判
- 大批次或不熟的拆分先 `dry_run: true` 看展开后的每条 prompt
- 批次结果中不达标的条目，用 `followups: [{index, followup}]` 追问（沿用该条上下文）；方向错的条目等批次结束后单独派 `Agent` 处理
- **接缝检查照做**（见第四节）：swarm 只保证逐项执行，跨条目的接口/类型/重复实现仍要主代理统一把关
- 有依赖的子任务**禁止**放进同一批次 —— 依赖链走串行 Agent 派遣
